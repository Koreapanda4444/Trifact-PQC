# TRIFACT — Post-Quantum Digital Signature Design

[English](TRIFACT_DESIGN.md) | [한국어](TRIFACT_DESIGN_KR.md)

> **Status: Draft / Experimental / Unproven**
>
> This document describes a research proposal. It does not claim post-quantum security or production readiness.

## 1. Overview

**TRIFACT** is an experimental post-quantum digital signature algorithm based on a hidden 1-factorization of a 3-uniform hypergraph.

Classification:

**Post-Quantum Digital Signature Algorithm**

Core computational problem:

**Random 3-Uniform Hypergraph Factorization Recovery Problem (R3HFR)**

The central idea of TRIFACT is to use a decomposition of a public hypergraph into multiple perfect matchings as the secret key.

An attacker does not need to recover the factorization originally generated by the key-generation algorithm.

**Recovering any valid 1-factorization of the public hypergraph constitutes a successful attack.**

---

## 2. Mathematical Object

Let the vertex set be

```math
V=\{0,\ldots,n-1\}.
```

The integer `n` is divisible by 3.

TRIFACT uses a **3-uniform hypergraph**, meaning that every hyperedge contains exactly three vertices:

```math
H=(V,E).
```

Each edge has the form

```math
e=\{v_a,v_b,v_c\}.
```

---

## 3. 1-Factor

A **1-factor** `F` of a 3-uniform hypergraph satisfies

```math
F\subseteq E,
```

and the following conditions:

- all hyperedges in `F` are pairwise vertex-disjoint;
- every vertex belongs to exactly one edge in `F`.

Therefore,

```math
|F|=\frac n3.
```

The concepts of a hypergraph 1-factor and 1-factorization are established objects in combinatorics.

---

## 4. 1-Factorization

Assume that the public hypergraph is `d`-regular. TRIFACT requires the entire edge set to decompose as

```math
E=F_1\;\dot\cup\;F_2\;\dot\cup\;\cdots\;\dot\cup\;F_d,
```

where every `F_i` is a 1-factor.

Every vertex therefore appears exactly once in each of

```math
F_1,\ldots,F_d.
```

The total number of edges is

```math
m=\frac{dn}{3}.
```

---

## 5. Secret Representation

Define a function that assigns a factor label to every hyperedge:

```math
c:E\rightarrow\{0,\ldots,d-1\}.
```

If `c(e)=j`, then

```math
e\in F_j.
```

A valid witness must satisfy, for every vertex `v`,

```math
\{c(e):v\in e\}=\{0,\ldots,d-1\}.
```

In other words, the `d` hyperedges incident to `v` must all have distinct factor labels.

This local condition implies that the entire edge set is partitioned into `d` perfect matchings.

---

## 6. Proposed Computational Problem

### Random 3-Uniform Hypergraph Factorization Recovery

Abbreviation:

**R3HFR**

### Instance

A `d`-regular 3-uniform hypergraph sampled from the TRIFACT KeyGen distribution, with all factor labels removed:

```math
H.
```

### Goal

Find any function

```math
c':E\rightarrow\{0,\ldots,d-1\}
```

such that, for every `v\in V`,

```math
\{c'(e):v\in e\}=\{0,\ldots,d-1\}.
```

Equivalently:

> Decompose the public hypergraph into `d` 1-factors.

The recovered factorization does not need to equal the one used by KeyGen.

---

## 7. Why the Problem Is Defined as Recovery

The security assumption is not

> recovering the original secret is difficult.

An alternative factorization

```math
c'\neq c
```

is also a valid signing witness.

The security assumption is therefore defined from the beginning as

```math
\boxed{\text{Find ANY valid factorization}}.
```

This definition directly incorporates the equivalent-secret problem.

---

## 8. KeyGen

Select

```math
(n,d)
```

according to the parameter set.

Let

```math
V=\{0,\ldots,n-1\}.
```

For each

```math
j\in\{0,\ldots,d-1\},
```

sample an independent random permutation

```math
\pi_j\in S_n.
```

Partition each permutation into consecutive triples:

```math
F_j=\{\{\pi_j(0),\pi_j(1),\pi_j(2)\},\ldots,
\{\pi_j(n-3),\pi_j(n-2),\pi_j(n-1)\}\}.
```

Each `F_j` is therefore a 1-factor by construction.

Combine all factors:

```math
E=\bigcup_{j=0}^{d-1}F_j.
```

If the same hyperedge occurs in different factors, reject the entire instance and restart KeyGen.

Finally, apply an independent random permutation

```math
\rho
```

to all vertices. This removes direct correlations between factor-generation order and vertex numbering.

### Public Key

```math
pk=H=(V,E).
```

### Secret Key

```math
sk=c,
```

where `c` is the factorization that records the factor containing each edge.

---

## 9. Important Properties of KeyGen

The public key reveals that the hypergraph is:

- 3-uniform;
- `d`-regular;
- composed of `dn/3` edges;
- guaranteed to have at least one complete 1-factorization.

The hidden information is the partition

```math
E=F_1\dot\cup\cdots\dot\cup F_d.
```

TRIFACT therefore does not rely on security through obscurity. The attacker is assumed to know the complete KeyGen algorithm and the public-key distribution.

---

## 10. Background of the Assumption

For general `r`-uniform hypergraphs, perfect-matching problems belong to computationally difficult problem families when `r\ge3`. Three-dimensional matching is NP-complete, and several NP-completeness results are known for hypergraph perfect matching.

This fact is **not a security proof for TRIFACT**.

TRIFACT requires the substantially stronger claim that

> R3HFR is hard on average over the special random `d`-regular hypergraph distribution produced by KeyGen.

This claim requires independent analysis.

---

## 11. Basic Signing Strategy

The signer does not reveal the secret factorization directly.

Instead, the signer proves knowledge of a witness `c` for the NP relation

```math
C_H(c)=1
```

using a zero-knowledge proof-of-knowledge construction.

Here, `C_H` is a verification relation that takes the public hypergraph `H` and an edge labeling `c`, and checks whether `c` is a valid factorization.

---

## 12. Factorization Relation

The relation

```math
R(H,c)=1
```

holds if and only if all of the following conditions are satisfied.

### Label Range

For every edge `e`,

```math
0\le c(e)<d.
```

### Local Uniqueness

For every vertex `v` and every pair of distinct incident edges

```math
e_i,e_j\ni v,
```

the labels satisfy

```math
c(e_i)\neq c(e_j).
```

Because `H` is `d`-regular and exactly `d` labels are available, this condition implies that every label appears exactly once at every vertex. Each label class is therefore a perfect matching.

---

## 13. Proof Layer

The current TRIFACT design does not attempt to invent a new zero-knowledge protocol at the same time as the underlying problem.

The R3HFR witness relation is proven using an **MPC-in-the-Head family proof of knowledge**.

Conceptually, the signer simulates several virtual MPC participants jointly evaluating the factorization-verification relation. The secret `c` is secret-shared among the participants so that no individual participant knows the entire witness.

The verification circuit evaluates

```math
R(H,c).
```

The execution view of each participant is committed.

---

## 14. One Proof Repetition

One proof repetition conceptually consists of the following steps.

### 1. Share

Split the secret witness

```math
c
```

into multiple shares.

### 2. Simulate

The virtual MPC parties evaluate

```math
R(H,c).
```

### 3. Commit

Commit to each party's:

- randomness;
- input share;
- communication;
- execution state.

### 4. Challenge

Hash the commitments and message to derive the verifier challenge.

### 5. Open

Reveal only the subset of MPC views required by the challenge.

### 6. Verify

The verifier checks the consistency of the opened views and verifies that the computation of

```math
R(H,c)=1
```

was performed correctly.

---

## 15. Non-Interactive Signature

In the signature scheme, the verifier does not send an interactive challenge.

A Fiat-Shamir-style transformation is used. For a message `M`, the challenge is conceptually

```math
ch=H(\text{domain}\parallel pk\parallel M\parallel salt\parallel commitments).
```

The signature therefore has the approximate form

```math
\sigma=(salt,commitments,opened\ views,auxiliary\ data).
```

---

## 16. Algorithm Interfaces

### KeyGen

```math
\operatorname{KeyGen}(params)\rightarrow(pk,sk).
```

Outputs:

```math
pk=H
```

and

```math
sk=c.
```

### Sign

```math
\operatorname{Sign}(sk,M)\rightarrow\sigma.
```

1. Use the factorization `c` corresponding to `pk`.
2. Generate the proof repetitions.
3. Generate transcript commitments.
4. Derive the challenge from the message `M` and transcript.
5. Open the requested views.
6. Encode the signature.

### Verify

```math
\operatorname{Verify}(pk,M,\sigma)\rightarrow\{0,1\}.
```

1. Validate the encoding.
2. Validate transcript commitments.
3. Recompute the challenge.
4. Check consistency of the opened MPC views.
5. Verify the opened proof execution.
6. Accept only if every check succeeds.

---

## 17. Correctness

The secret key `c` generated by an honest KeyGen satisfies

```math
R(H,c)=1
```

by construction.

An honest signer can therefore always generate a valid proof transcript. The target correctness property is

```math
\Pr[\operatorname{Verify}(pk,M,\operatorname{Sign}(sk,M))=1]=1.
```

The design targets a structure with no cryptographic correctness failures.

---

## 18. Security Assumptions

TRIFACT relies on three main layers of assumptions.

### Assumption A — R3HFR

Given only a public key `H` sampled from the KeyGen distribution, finding any valid factorization `c'` is difficult.

This is the core new assumption.

### Assumption B — Proof of Knowledge

It must be possible to extract a witness satisfying

```math
R(H,c')=1
```

from an attacker that can repeatedly generate valid proofs.

### Assumption C — Symmetric Primitives

The hash/XOF constructions used for commitments and the Fiat-Shamir transcript must provide the required level of security against quantum attackers.

---

## 19. Final Security Goal

The target signature security notion is

```math
EUF\text{-}CMA.
```

Even after obtaining valid signatures for chosen messages, an attacker should be unable to produce a signature for a new message `M^*` such that

```math
\operatorname{Verify}(pk,M^*,\sigma^*)=1.
```

---

## 20. Intended Security Argument

The intended reduction has the following form:

```text
TRIFACT Forgery
       ↓
PoK Extraction
       ↓
Valid Factorization Recovery
       ↓
R3HFR Break
```

If a valid factorization witness can be extracted from a successful signature forgery, the forgery can be converted into an R3HFR attack.

**TRIFACT does not currently claim to have a formal security proof.**

---

## 21. Main Attack Models

The R3HFR analysis must consider at least the following attacks.

### Perfect-Matching Peeling

Find one perfect matching, remove it,

```math
H\rightarrow H-F_1,
```

and repeat.

### Exact Cover

Convert the search for one factor into an exact-cover problem.

### SAT / SMT / ILP

Assign a factor-label variable to every edge and directly solve constraints of the form

```math
c(e_i)\neq c(e_j).
```

This attack is particularly important.

### Global Edge Coloring

Solve R3HFR directly as a specialized hypergraph edge-coloring problem.

### Meet-in-the-Middle

Split the vertex or edge set, construct partial factorizations, and combine them.

### Factor Swapping

Search for small alternating structures that permit edges to be exchanged between factors while preserving a valid factorization.

This may provide an efficient way to construct equivalent witnesses.

### Statistical Recovery

Exploit statistical correlations that may remain because KeyGen constructs each factor from an independent random permutation.

### Automorphism Attack

Use automorphisms of the public hypergraph to reduce the factorization search space.

### Quantum Search

Consider not only Grover search and amplitude amplification, but also possible quantum-walk and quantum-backtracking speedups for factorization search.

---

## 22. Primary Risk

The largest unresolved question is explicit:

> **Is factorization recovery actually difficult on average for the random union-of-perfect-matchings distribution produced by KeyGen?**

Worst-case NP-hardness of general hypergraph matching is insufficient. Hypergraphs generated by KeyGen may be substantially easier to factor than general instances.

If efficient recovery is found, the current TRIFACT design must be abandoned.

---

## 23. Secondary Risk: Number of Factorizations

A public key may admit too many valid factorizations.

Let

```math
N_H=|\{c:R(H,c)=1\}|.
```

If `N_H` is very large, the attacker does not need to recover a particular secret, and the search cost may be substantially reduced.

The design does not simply require `N_H=1`. Instead, parameter selection must consider the relationship between valid-witness density and attack cost.

---

## 24. Tertiary Risk: Signature Size

MPC-in-the-Head constructions may produce large signatures.

TRIFACT's practicality is therefore determined by:

- factorization-witness size;
- verification-circuit size;
- number of proof repetitions.

Even a strong underlying problem would have limited competitiveness if signatures grow to tens or hundreds of kilobytes.

---

## 25. Parameter Structure

Because no concrete security estimates have been validated, the design does not yet use names such as `128`, `192`, or `256`.

A parameter set is initially represented as

```math
P=(n,d,\tau,R),
```

where:

- `n` is the number of vertices;
- `d` is the number of factors and the degree of every vertex;
- `\tau` denotes structural rejection conditions;
- `R` is the number of proof repetitions.

Category 1/3/5 parameter sets may be selected only after concrete cryptanalysis.

---

## 26. Initial Design Direction

The underlying problem is fixed to **3-uniform** hypergraphs.

Reducing to 2-uniform graphs removes the intended asymmetry because graph perfect matching is efficiently solvable. Increasing the uniformity too far enlarges both the public key and relation circuit.

The initial choice is therefore

```math
r=3.
```

---

## 27. Public-Key Representation

The canonical representation is a list of sorted triples.

Within every edge

```math
\{a,b,c\},
```

the vertices are ordered so that

```math
a<b<c.
```

The complete edge list is sorted lexicographically. The same hypergraph therefore always has the same byte representation.

Factor labels are not included in the public key.

---

## 28. Secret-Key Representation

The secret is an array containing the factor label of every edge index in the canonical public-key order:

```math
sk=(c_0,\ldots,c_{m-1}).
```

Factor names have no intrinsic meaning. Every global permutation of

```math
0,\ldots,d-1
```

therefore represents an equivalent secret.

This symmetry must be included in the security analysis.

---

## 29. Domain Separation

Every cryptographic hash context is separated.

Logical domains include:

```text
TRIFACT/KEYGEN
TRIFACT/COMMIT
TRIFACT/MPC
TRIFACT/CHALLENGE
TRIFACT/SIGN
TRIFACT/EXPAND
```

Different protocol stages do not share the same hash domain.

---

## 30. Stateless Signing

TRIFACT targets stateless signing.

Every signature uses an independent

```math
salt
```

and fresh proof randomness.

A hedged-generation construction addressing randomness failure is deferred to later security design.

---

## 31. Kill Criteria

The current R3HFR-based design is abandoned if any of the following is found.

### Immediate Abandonment

- polynomial-time factorization on the KeyGen distribution;
- very low practical scaling of SAT/ILP attacks;
- a statistical distinguisher that reveals the factorization;
- easy generation of valid factorizations through small local swaps;
- insufficient attack-cost growth as parameters increase;
- an effective quantum structural algorithm.

### Major Redesign Required

- an impractically large Category 1 public key;
- an impractically large signature;
- an excessively large verification circuit;
- excessive proof-repetition cost.

---

## 32. Difference from Existing PQC Families

TRIFACT is not based on:

- lattices;
- LWE/SIS;
- error-correcting-code decoding;
- multivariate polynomial solving;
- hash-tree signatures;
- isogenies.

Its central secret is

```math
\boxed{\text{hypergraph 1-factorization}},
```

and its core attack problem is

```math
\boxed{\text{R3HFR}}.
```

Recent post-quantum signature research includes proposals that introduce a new problem, such as Matrix Subcode Equivalence, and connect it to an MPC-in-the-Head or VOLE-in-the-Head signature. The general research pattern of **a new search problem combined with a generic ZK/PoK layer** is therefore a legitimate direction for PQC research.

---

## 33. Novelty Status

The initial literature search found work on:

- combinatorial properties of hypergraph 1-factorization;
- authentication ideas based on hypergraph isomorphism;
- post-quantum signatures based on subgraph isomorphism.

However, the initial search did not identify an identical proposal that

> treats hidden 1-factorization recovery in a random regular 3-uniform hypergraph as the core average-case assumption and builds a post-quantum digital signature from it.

The current novelty label is therefore:

**Potentially novel — formal prior-art review required**

No claim of being the first proposal is made.

## 36. Conclusion

The core construction of TRIFACT is

```math
\boxed{\text{random perfect matchings}\rightarrow
\text{remove factor labels}\rightarrow
\text{public hypergraph}}.
```

The secret key is

```math
\boxed{\text{hidden 1-factorization}},
```

and the attack problem is

```math
\boxed{\text{recover any valid factorization of the public hypergraph}}.
```

Instead of revealing the factorization, the signer binds a proof of knowledge of a valid factorization to the message.

The viability of TRIFACT therefore depends on one question:

> **Is R3HFR sufficiently difficult against both classical and quantum attacks on average over the KeyGen distribution?**

If the answer is yes, TRIFACT can be developed further. If the answer is no, the underlying design must be abandoned.
